## 2. 需要修复 / 对齐的具体项

### P0 — 与 prompt 明显冲突，建议尽快修

#### 2.1 Module 5：MySQL → ES 双写未接入业务写路径
- 现象：[ProductSearchService.upsert/delete](../src/main/java/com/nexusmart/seckill/search/ProductSearchService.java) 暴露了接口，但 `GoodsService`、任何写商品的代码都**没有调用**它。运行期商品变更不会进 ES，只有启动期 `reindexAll` 生效。
- 修复方案：
    - 在商品新增 / 更新 / 下架的 Service 方法里调用 `productSearchService.upsert(goods)` / `delete(id)`。
    - 写入失败应**只记日志，不影响主交易**（ES 是检索增强组件）。
- 关联文件：
    - [src/main/java/com/nexusmart/seckill/search/ProductSearchService.java](../src/main/java/com/nexusmart/seckill/search/ProductSearchService.java)
    - [src/main/java/com/nexusmart/seckill/service/GoodsService.java](../src/main/java/com/nexusmart/seckill/service/GoodsService.java)

#### 2.2 Module 5：`ProductDocument.description` 字段被占位
- 现象：[ProductSearchService.toDocument:118](../src/main/java/com/nexusmart/seckill/search/ProductSearchService.java#L118) 把 `description` 直接设为 `goods.getGoodsName()`，因为 `Goods` 实体根本没有描述列。结果是 `multi_match(name^3, description)` 退化成单字段检索。
- 修复方案（二选一）：
    - **A**：给 `goods` 表加 `description` 列 + Entity 映射 + DDL 迁移，真正使用多字段。
    - **B**：把 `multi_match` 改成只查 `name`，并删除 `ProductDocument.description` 字段，避免误导。
- 关联文件：
    - [src/main/java/com/nexusmart/seckill/entity/Goods.java](../src/main/java/com/nexusmart/seckill/entity/Goods.java)
    - [src/main/java/com/nexusmart/seckill/search/ProductDocument.java](../src/main/java/com/nexusmart/seckill/search/ProductDocument.java)
    - [src/main/java/com/nexusmart/seckill/search/ProductSearchService.java](../src/main/java/com/nexusmart/seckill/search/ProductSearchService.java)
    - [docker/mysql/init/001_schema.sql](../docker/mysql/init/001_schema.sql)

#### 2.3 Module 10：限流 `blockHandler` 未返回 HTTP 429
- 现象：[GoodsController.getProductDetailBlocked:50](../src/main/java/com/nexusmart/seckill/controller/GoodsController.java#L50)、[ProductSearchController.searchBlocked:48](../src/main/java/com/nexusmart/seckill/controller/ProductSearchController.java#L48) 都用 `Result.error(...)` 返回，HTTP 状态码仍是 200。prompt 明确要求「触发限流时返回 HTTP 429」。
- 修复方案：把 `blockHandler` 的返回类型改为 `ResponseEntity<Result<...>>`，限流分支返回 `ResponseEntity.status(HttpStatus.TOO_MANY_REQUESTS).body(...)`。
- 关联文件：
    - [src/main/java/com/nexusmart/seckill/controller/GoodsController.java](../src/main/java/com/nexusmart/seckill/controller/GoodsController.java)
    - [src/main/java/com/nexusmart/seckill/controller/ProductSearchController.java](../src/main/java/com/nexusmart/seckill/controller/ProductSearchController.java)

#### 2.4 Readme 路线图与代码现状冲突
- 现象：[Readme.md:438-443](../Readme.md#L438-L443) 仍把 Module 5 / 7 / 10 标为未完成（`[ ]`），并写 "Module 10 当前由 Resilience4j 承担"。CHANGELOG-2026-05-15 已经补齐这三个模块。

- 关联文件：[Readme.md](../Readme.md)

### P1 — 与 prompt 偏离但有合理理由，建议补说明 / 二期优化

#### 2.5 Module 1：Dockerfile 不支持 `SERVER_PORT` 环境变量
- 现象：[Dockerfile:32](../Dockerfile#L32) `EXPOSE 8081` 写死，`ENTRYPOINT` 也没有把 `SERVER_PORT` 传给 JVM。
- 修复方案：
    - `EXPOSE ${SERVER_PORT:-8081}` 或保留 8081 但在 entrypoint 里加 `-Dserver.port=${SERVER_PORT:-8081}`。
    - `HEALTHCHECK` 里的 `localhost:8081` 同步改成 `${SERVER_PORT:-8081}`。
- 关联文件：[Dockerfile](../Dockerfile)

#### 2.6 Module 1：只有单个 `app` 实例，nginx 负载均衡形同虚设
- 现象：[docker-compose.yml:216](../docker-compose.yml#L216) 只有一个 `app`；[nginx.conf:53-56](../nginx.conf#L53-L56) upstream 只有 `server gateway:8080;`。三种负载算法只在注释里展示，没有可切换的 active 配置。CHANGELOG-2026-05-14 解释为「由 Nacos lb 替代静态 upstream」。
- 修复方案（按需求选一）：
    - **保持现状**：在 README 和 nginx.conf 里加显眼说明「单实例 + Nacos lb，prompt 中『Nginx 两实例』未落地」。
    - **完整落地**：补一个 `app-2`（端口 8082）+ `ID_WORKER=2` 避免雪花冲突，nginx upstream 加 `server app:8081; server app-2:8082;` 并提供 3 套 active 配置切换。
- 关联文件：[docker-compose.yml](../docker-compose.yml)、[nginx.conf](../nginx.conf)

#### 2.7 Module 4：未使用 ShardingSphere-JDBC
- 现象：prompt 明确要求 ShardingSphere-JDBC 的读写分离规则，当前是 [DataSourceRoutingAspect](../src/main/java/com/nexusmart/seckill/config/datasource/DataSourceRoutingAspect.java) + `AbstractRoutingDataSource` 的自研方案。
- 修复方案（二选一）：
    - **保持现状**：在 README 和 CHANGELOG 里更显眼地说明「功能等价、保持读写分离主干由自研 AOP 承担」。
    - **二期合并**：把读写分离规则也下沉到 `sharding.yaml`，与 Module 7 的分库分表共用同一份 ShardingSphere 数据源，删除 AOP。
- 关联文件：
    - [src/main/java/com/nexusmart/seckill/config/datasource/](../src/main/java/com/nexusmart/seckill/config/datasource/)
    - [src/main/resources/sharding.yaml](../src/main/resources/sharding.yaml)

#### 2.8 Module 7：主订单 `order_info` 未分片
- 现象：分片只作用于独立的 `order_archive` 逻辑表，主交易链路（`SeckillOrderAsyncService.createOrderInTransaction`）仍写 `order_info`，走主从。
- 修复方案：
    - **保持现状**：在 CHANGELOG / AUDIT 里说明「分库分表作为演示 profile，未替换主订单」。
    - **二期合并**：在 `sharding.yaml` 增加 `order_info` 规则，把 `OrderInfoMapper` 也走 ShardingSphere 数据源。需要同步处理 `seckill_order`（防重表）和跨库事务。
- 关联文件：
    - [src/main/java/com/nexusmart/seckill/sharding/](../src/main/java/com/nexusmart/seckill/sharding/)
    - [src/main/java/com/nexusmart/seckill/service/SeckillOrderAsyncService.java](../src/main/java/com/nexusmart/seckill/service/SeckillOrderAsyncService.java)

#### 2.9 Module 8：未实现 `outbox` 本地消息表
- 现象：prompt 明确要求基于本地消息表的最终一致性。当前用 Redis ZSet `seckill:pending:index` + 定时补偿替代。在 Redis 数据丢失（AOF/RDB 异常）场景下，pending 消息会一起丢失。
- 修复方案：
    - 加一张 `outbox` 表：`(id, request_id, order_no, payload, status, retry_count, next_retry_at, created_at)`。
    - 入口事务里**同时**写 `outbox`（PENDING）和业务订单，由独立 Worker / Kafka Producer 扫描发送，成功后置 SENT。
    - DLT 消费失败时把 `outbox.status` 置 FAILED，补偿任务读 `outbox` 而不是 Redis ZSet。
- 关联文件：
    - 新建 `src/main/resources/db/migration/V20260516_xx__outbox.sql`
    - 改造 [SeckillService.submitSeckill](../src/main/java/com/nexusmart/seckill/service/SeckillService.java)、[SeckillCompensationService](../src/main/java/com/nexusmart/seckill/service/SeckillCompensationService.java)

#### 2.10 Module 8：Kafka 未启用事务消息
- 现象：[SeckillOrderProducer:39](../src/main/java/com/nexusmart/seckill/service/SeckillOrderProducer.java#L39) 使用普通 `kafkaTemplate.send`。prompt 在「订单支付 + 订单状态更新」段要求 `Spring @Transactional + Kafka 事务消息` 保证原子性。
- 修复方案：
    - `KafkaTemplate` 配置 `transactional-id-prefix`，`Producer` 启用 `enable.idempotence=true`、`transactional.id`。
    - 关键写消息的方法加 `@Transactional`（Spring 会接管事务边界）。
- 关联文件：[src/main/java/com/nexusmart/seckill/config/KafkaSeckillConfig.java](../src/main/java/com/nexusmart/seckill/config/KafkaSeckillConfig.java)

#### 2.11 Module 8：限购语义偏二元
- 现象：当前 [SeckillService](../src/main/java/com/nexusmart/seckill/service/SeckillService.java#L25) 用 SADD 实现「同商品一人一单」。prompt 在 Module 8.2① 提到「每个用户限购数量校验（`seckill:user:buy:{userId}:{productId}` 计数）」，是**可配置数量阈值**，不是二元。
- 修复方案：把 Lua 脚本里 `SISMEMBER` 改成 `INCR seckill:user:buy:{userId}:{seckillId}` + 与 `limit-per-user` 比较，超限回滚。配置项 `app.seckill.limit-per-user` 接入 Nacos。
- 关联文件：[src/main/java/com/nexusmart/seckill/service/SeckillService.java](../src/main/java/com/nexusmart/seckill/service/SeckillService.java)
